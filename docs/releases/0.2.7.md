# GoOS 0.2.7

GoOS 0.2.7 is the remote-administration release.

Starting from the 0.2.6 HTTPS/trust baseline, this release adds native SSH remote terminals, isolates host-key signing from workers, fixes terminal/session correctness over real OpenSSH clients, adds non-interactive SSH command execution, live PTY resize, structured log following, authorized-key administration, a set of bounded native administration tools, and a dedicated Proxmox acceptance path.

The release is still in preparation. The final exact-candidate Proxmox run is the last acceptance step.

## 1. Native SSH remote terminals

GoOS now provides a native SSH service through `remoted`.

The service supports:

- Ed25519 public-key authentication;
- `curve25519-sha256` key exchange;
- `ssh-ed25519` host keys;
- `aes128-gcm@openssh.com`;
- one SSH session channel per connection;
- interactive PTY shell sessions;
- `window-change`, EOF, close and rekey handling;
- bounded handshake and authenticated-session limits.

Typical interactive use:

```sh
ssh -i ~/.ssh/id_ed25519 user@GOOS_ADDRESS
```

`remoted` owns the listener. PID 1 owns shell/session/job lifecycle. Accepted connections are handed to bounded `remoted-worker` instances; shells do not receive TCP authority.

The SSH service deliberately does **not** implement SFTP/SCP, agent forwarding, X11 forwarding or TCP forwarding.

See [remote access](../development/remote-access.md) and [ADR 0199](../adr/0199-native-remote-terminal-sessions.md).

## 2. Host identity and signing isolation

SSH host private material is no longer exposed to session workers.

The controller owns host identities and creates a dedicated non-transferable signing endpoint for each worker. Workers receive only the public host key, public authorized-key policy, session limits and a signing endpoint.

The worker sends the 32-byte SSH exchange hash to the controller and receives an Ed25519 signature. It verifies that signature against the public host key before continuing the handshake.

The identity pool keeps retired keys alive only while existing workers still use them and zeros them after the final reference is released. Failed replacement identity candidates do not replace the current host identity.

If a signer peer dies, the corresponding worker is revoked and closed instead of continuing with a broken or fallback signing path. Validation builds include signer-peer fault injection so this lifecycle is exercised by the remote gate.

Host identity is persistent on disk and must remain stable across reboot. `remote status` exposes only the public SHA256 fingerprint.

## 3. SSH terminal and session correctness

Several terminal/session issues found with real OpenSSH clients were fixed after the first SSH implementation.

### Cooked PTY line endings

Remote cooked output now translates bare LF to CRLF while preserving existing CRLF and raw-mode bytes. This removes the classic OpenSSH staircase output:

```text
goos>
      goos>
            goos>
```

The normalization keeps state across output chunks and is applied only to the remote cooked PTY path.

### Output ordering before prompts

The remote worker now drains a bounded batch of pending stdout before servicing the next terminal prompt request. This prevents stream chunk boundaries from appearing as arbitrary visible line breaks in commands such as `log`.

The worker remains bounded and continues servicing SSH protocol/control work between stdout batches.

### Serial newline normalization

COM1 output now has one canonical newline-normalization layer. Bare LF is converted to CRLF for serial output, existing CRLF is preserved, and framebuffer output remains byte-for-byte unchanged.

This fixes diagonal output when GoOS is used through Proxmox `qm terminal` or other host PTY frontends.

### Remote `exit`

The shell now implements:

```text
exit
```

for remote sessions. It flushes output and terminates the SSH shell cleanly with status 0.

Local serial/framebuffer shells refuse `exit` so the supervised local shell is not intentionally dropped into an immediate restart loop.

### Graceful remote reboot and poweroff

Remote `reboot` and `poweroff` are coordinated with PID 1:

1. storage is synchronized;
2. the remote shutdown request is accepted;
3. the requesting shell exits;
4. SSH output/channel shutdown completes;
5. PID 1 waits for the requester worker to disappear, bounded by a grace deadline;
6. the machine reset/poweroff operation is performed.

This removes OpenSSH timeout/broken-pipe shutdowns while preserving immediate local-console lifecycle behavior.

Unsupported poweroff or synchronization failures keep the SSH session alive and report the failure instead of closing the only administration channel.

## 4. Non-interactive SSH command execution

SSH now supports standard non-PTY `exec` requests:

```sh
ssh -T user@GOOS_ADDRESS uname
ssh -T user@GOOS_ADDRESS 'net status'
ssh -T user@GOOS_ADDRESS 'log -n 5'
printf 'needle\n' | ssh -T user@GOOS_ADDRESS 'grep needle'
```

The request is executed by the existing native GoOS shell parser. There is no `/bin/sh -c` compatibility layer.

The one-shot shell:

- starts without a terminal handle;
- uses separate stdin/stdout/stderr streams;
- supports the native shell's bounded sequences, pipelines and redirections;
- returns the native command status through SSH `exit-status`;
- drains stdout/stderr before channel close;
- rejects malformed/oversized exec requests;
- rejects `pty-req + exec`;
- rejects unquoted background `&` before any command is started.

Interactive SSH shell behavior remains unchanged.

## 5. Native administration commands

Eight bounded native administration images are added:

```text
head [-n N] FILE
tail [-n N] FILE
grep [-i] PATTERN [FILE]
wc [-l|-w|-c] [FILE]
find PATH [-name NAME]
hexdump FILE
hostname [NAME]
date [-u]
```

These are GoOS-native utilities, not GNU compatibility implementations.

Highlights:

- `head` and `tail` default to 10 lines;
- `tail` uses bounded storage and has no follow mode;
- `grep` performs literal substring matching with optional ASCII case folding, not regular expressions;
- `grep` and `wc` read stdin when FILE is omitted;
- `find` performs bounded recursive traversal and exact basename matching;
- `hexdump` prints fixed offset/hex/ASCII rows;
- `hostname` reads or persists `system.hostname`;
- `date` prints the current realtime UTC value.

The hostname is a single ASCII label of 1..63 letters, digits or hyphens, with no leading/trailing hyphen.

`hostname NAME` uses a new scoped acknowledged durable config mutation. Existing `config set` semantics are unchanged.

See [shell documentation](../userspace/shell.md).

## 6. Structured system log filtering and follow

The shell `log` builtin now supports bounded structured filtering:

```text
log
log -n 20
log --level warn
log --component remoted
log -n 50 --level error
log -f --component remoted
```

Filtering uses structured log fields rather than reparsing formatted text.

The kernel log ring exposes absolute sequence information. A new cursor-aware wait form lets a log follower block in the same wait as terminal cancellation without polling and without changing the existing WaitAny ABI.

Each follower owns its own cursor. Ring overwrite is detected and reported as a gap, after which the reader resumes from the oldest retained record.

`Ctrl-C` exits `log -f` and returns to the same shell.

The ring retains 64 records.

Because `log` is a shell builtin, it is not a pipeline stage. Use its structured filters directly instead of `log | grep ...`.

## 7. Live PTY resize for running native TUI applications

SSH `window-change` now reaches the currently running foreground native TUI application without restarting it.

The resize path is:

```text
OpenSSH window-change
        -> remoted-worker
        -> terminal geometry state
        -> PID 1 foreground resize route
        -> running native TUI
```

Geometry snapshots/events carry a monotonic sequence. A foreground application receives snapshot N at launch and only applies later events with a newer sequence, so a resize racing with launch cannot be overwritten by an older startup snapshot.

The current foreground raw-terminal application receives the resize endpoint; background jobs do not.

Nested launch is also handled: when a TUI starts another foreground TUI, resize ownership follows the nested application and the parent receives the newest geometry when control returns.

`gfm`, `gview` and `edit` redraw in place when the host terminal is resized.

## 8. SSH authorized-key administration

Authorized SSH keys can now be managed from GoOS:

```text
remote keys
remote key add "ssh-ed25519 AAAA... comment"
remote key remove SHA256:...
```

The editor accepts Ed25519 public keys only, preserves valid existing entries/comments, rejects duplicates, removes exactly one full SHA256 fingerprint match, and keeps the existing 64 KiB file, 64-key and 4096-byte line bounds.

Key changes use a dedicated PID 1 guard and confined VFS authority. Staging and previous-content files are reread and verified before publication. The running remote policy is reloaded only after the candidate has been committed.

If reload fails, the previous effective policy remains active and persisted content is restored while transaction ownership is still valid. Rollback does not overwrite an unrelated concurrent edit.

The `remote` administration command receives no SSH host private-key authority.

Established SSH sessions remain alive after their admission key is removed; new connections use the committed key set.

## 9. Proxmox/KVM remote-administration acceptance

The Proxmox lab tooling now has a dedicated retained-VM remote administration scenario.

It validates, on one real KVM/Proxmox guest:

- serial administration commands;
- persistent hostname;
- SSH host identity pinning;
- non-PTY SSH exec stdout/stderr/exit status;
- background-exec rejection;
- PTY+exec rejection using a real sized host PTY;
- `log -f` wakeup and Ctrl-C cancellation;
- live `gfm` terminal resize;
- clean interactive `exit`;
- authorized-key add/list/auth/remove/refusal;
- denial of SSH host-private-key reads;
- clean reboot and reconnect;
- host identity persistence across reboot;
- clean SSH poweroff and final VM power state;
- retained serial/report/artifact evidence.

The scenario creates disposable Ed25519 client keys and obtains the expected GoOS host fingerprint from trusted serial `remote status`. The scanned host key is accepted only after matching that fingerprint, then every automated OpenSSH call uses `StrictHostKeyChecking=yes`.

The remote QEMU gate also exercises the SSH/session/security contract across two persistent boots.

## 10. Developer tooling and portable scratch paths

Build/test tooling no longer depends on one developer-specific `/Volumes/Data/tmp` directory.

Temporary compatibility roots, test fixtures and reports now live under the repository-local ignored tree:

```text
build/tmp/
```

Repository/build discovery is shared and bounded. Compatibility tools keep canonical containment and symlink protections and now authorize generated roots only under the GoOS repository `build/` directory.

This applies to TLS/SSH/crypto compatibility tooling, remote/TLS/trust boot tests, OpenSSH host tests and related fixtures.

Documentation and tests were updated so checkout paths are portable across macOS/Linux machines.

## 11. Validation status

At the current 0.2.7 release-candidate stage:

- `go test ./...` passed;
- `make test-race` passed;
- focused race/vet/SSH compatibility host tests passed;
- the extended QEMU remote gate passed 210 assertions over two persistent boots;
- the network regression passed 207 checks;
- console-GUI regression passed console, keyboard, filesystem, file-manager, interrupt, viewer and nested-launch coverage.

Crypto feasibility targets retain their existing known semantics:

- with `CRYPTO_COMPAT=0`, stock ASN.1/X.509 feasibility builds still hit the existing unsupported TinyGo/UEFI runtime paths;
- with the runtime overlay, the other 13 probes pass;
- stock TinyGo TLS still fails its availability/no-wire probe and therefore `make test-crypto` remains expected-nonzero.

This is not a new 0.2.7 crypto regression. The selected native TLS implementation is the pinned software stack introduced in 0.2.6 and is validated by `make test-tls`.

The final exact-candidate Proxmox remote-administration run is still required before tagging the release. Full release acceptance should be attached to the exact final SHA; evidence from an earlier candidate must not be reused after runtime artifact changes.

## 12. Out of scope / known limits

This release does not add:

- SFTP/SCP;
- SSH agent, X11 or TCP forwarding;
- a POSIX shell;
- Linux PTYs or interactive Linux TUI programs;
- IPv6;
- dynamic linking;
- Linux socket/networking syscalls.

The native remote shell and native administration surface are intentionally bounded. Linux terminal compatibility remains future work.
