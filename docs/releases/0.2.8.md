# GoOS 0.2.8

GoOS 0.2.8 is the reclaimable and concurrent native-userspace release.

Starting from the 0.2.7 remote-administration baseline, this release replaces the old native userspace bump-allocation discipline with a reclaiming heap, measures and tunes that allocator, adds native threads, adds a GoOS-owned M:N goroutine runtime for selected TinyGo images, makes the concurrent VFS the production default, hardens stop-the-world collection and failure recovery, and adds deterministic validation of context-save boundaries and register roots.

## 1. Reclaimable native userspace memory

Native userspace now reclaims ordinary Go allocations instead of depending on request-scoped heap rewinds.

The runtime provides:

- size-classed slab allocation for objects up to 2 KiB;
- page-run allocation for larger objects;
- allocator metadata outside payload pages;
- a real `runtime.free`;
- synchronous `runtime.GC`;
- `runtime.ReadMemStats`;
- a per-process stop-the-world, non-moving, conservative mark-and-sweep collector;
- pointer-free allocation tracking from TinyGo layout information;
- free-page return through `VMDiscard`;
- `arena.Region` for explicitly scoped scratch outside the collected heap.

The original single-thread collector finds roots from linker-bracketed mutable globals, the current stack and registers, and live region memory. ADR 0203 and ADR 0204 extend that model to native threads and goroutine stacks.

Long-running services now use collected allocation rather than the old `Current`/`Reset` request rewind pattern. Idle waits can trigger collection after allocation activity, so services converge toward their live heap instead of retaining garbage until a later allocation threshold.

The kernel does not gain a collector and keeps the allocation discipline of ADR 0065.

## 2. Allocator measurement and tuning

The allocator now exposes enough diagnostics to tune it from measured workloads rather than from a guessed size distribution.

`arena.ReadDiagnostics` and versioned `ALLOC_PROFILE` records report page use, slab state, request sizes, reuse, discard/trim activity, lock/rendezvous counters and collection timing. `tools/allocreport`, `make bench-allocator` and the guest allocator benchmark turn those records into retained reports.

Measurements led to several changes:

- a 1360-byte size class was added for the VFS-heavy request range between 1024 and 2048 bytes;
- size-class and slots-per-page lookup tables replace repeated searches/divisions on common paths;
- slabs track the first bitmap word that may contain a free slot;
- untouched zero pages avoid unnecessary slot clearing;
- collection scrubs a bounded area below its own stack frame to reduce false retention from stale conservative roots;
- the scrub is bounded by the actual stack base and checked by `tools/stackframes`;
- free-page retention is configurable but remains disabled by default because the measured guest workload was faster that way;
- retained pages are trimmed during idle collection and before out-of-memory handling.

The memory gate now includes longer leak/endurance checks and allocator-profile completeness checks.

## 3. Native userspace threads

A native process may now run several kernel-scheduled tasks in one address space through `userspace/runtime/thread`.

The native thread ABI adds:

- `ThreadCreate`;
- `ThreadExit`;
- `ThreadJoin`;
- `ThreadSelf`;
- `ThreadYield`;
- runtime-private `ThreadSuspend` and `ThreadResume` for collector rendezvous.

There are 16 native thread slots including the main thread; process task quotas can impose a lower practical limit. Each additional thread receives a kernel-created 512 KiB stack above a 64 KiB guard.

Threads share the process heap, globals, handles, capabilities and quotas while keeping task identity, stack, syscall scratch, region state and allocator state per thread.

Generation-safe thread IDs prevent a joined or exited thread from naming a later occupant of the same slot. `Exit` remains process-wide; `ThreadExit` retires only the calling sibling.

## 4. Stop-the-world collection across native threads

The userspace collector now stops all sibling native threads before marking.

`ThreadSuspend` holds the process's other tasks off their processors and returns snapshots containing their saved instruction/stack pointers, general-purpose registers and XMM state. The runtime scans each accepted thread stack, its snapshot registers, globals and live regions before sweeping.

Collection fails closed: an incomplete suspension, inconsistent context, allocator fast-path window or region-transition window causes the runtime to resume and retry or abandon that collection instead of sweeping with incomplete roots.

The allocator becomes thread-aware after a second native thread exists. Threads can own one slab per size class, allocate/free locally without taking the process heap lock, and record remote frees in the slab bitmap. A collection takes owned slabs back before sweep.

Validation covers thread creation/join/slot reuse, faults and guard overflows, shared roots, region-transition windows, collection storms, allocator ownership and KVM execution on several processors.

## 5. Native M:N goroutines

GoOS now has a dedicated goroutine-enabled TinyGo target rather than trying to reuse TinyGo's platform scheduler unchanged.

A source-pinned overlay builds a separate native runtime with:

- `go` statements;
- channels and `select`;
- the `sync` primitives used by shipped code;
- timers and `time.Sleep`;
- local and global runnable queues;
- work stealing;
- bounded worker creation;
- `GOMAXPROCS` execution permits;
- cooperative scheduling and timer-driven preemption.

Goroutines run over native GoOS threads. Each G owns a guarded 256 KiB stack; stack reservations are batched so sleeping goroutines do not exhaust the process region table. Each M has its own scheduler stack and FS-based runtime control block.

The ordinary native target remains available and does not implicitly gain goroutines. Images opt into the goroutine target when they need this runtime.

## 6. Goroutine-aware GC, waits and I/O

The collector now accounts for G/M state as well as kernel task snapshots.

During an accepted stop-the-world rendezvous, a lockless runtime stack plan maps each held RSP to its native M scheduler stack or currently running G stack, adds switched-out G stacks and dormant M stacks, and refuses the collection if it cannot account for the state safely.

Kernel snapshots include XMM state because asynchronously interrupted TinyGo code may keep live pointer-bearing values in vector registers. Region Enter/Leave uses a separate collector window in addition to migration pinning so a collection cannot observe a half-published region state.

Blocking operations used by goroutine-enabled code now park the G rather than unnecessarily occupying its native worker where the contract permits it. This includes process waits, thread joins, log-cursor waits and interrupt waits. Thread joins can be reserved with process-owned tokens so migration cannot transfer an exclusive join claim accidentally.

The userspace library concurrency audit now records package-level shared state, ownership contracts, callback/reentrancy rules and the evidence for those contracts.

## 7. Concurrent VFS and fenced recovery

The VFS now uses the goroutine runtime by default.

Its ingress owner admits a bounded read set to two workers while keeping mutation, namespace, session-close and control operations behind ordered barriers. Read planning and cursor commit are separate, so RAMFS and image reads can overlap without making cursor updates unordered. Each session still has at most one admitted request.

Persistent filesystem transport remains serialized. If an accepted exchange becomes ambiguous, the VFS quarantines the shared cache, detaches the filesystem and refuses unsafe cache reuse while local reads continue.

Recovery now uses an independent supervisor endpoint and a fenced reattach:

1. the VFS reports the lost attachment generation;
2. PID 1 creates a fresh control route;
3. the VFS acknowledges the drained handoff;
4. a stalled old filesystem service is killed and PID 1 waits for the whole process to exit;
5. the replacement attaches only with an exit fence proving earlier instances are gone;
6. the cache page index starts empty before persistent data is served again.

Recovery attempts are bounded. An old or superseded notice cannot overwrite a newer attachment.

`VFS_RUNTIME=serial` remains available as a fallback, and `make test-vfs-serial` runs the full boot regression against it.

## 8. Concurrency and preemption hardening

The new validation load exposed several defects that simpler tests had not reached.

### Preemption vector state

The asynchronous goroutine preemption entry originally made its native call before saving SSE state. The native function-call path is allowed to clobber XMM registers, so interrupted TinyGo code could resume with corrupted vector state.

This produced two apparently unrelated failures: a null VFS slice in `ramfs.MakeName` and an allocator slab-count mismatch while SSE2 popcount code was running.

`goos_preempt_entry` now saves the interrupted FPU/SSE image before the kernel call and restores it after the preemption path. A dedicated vector-spin probe checks that asynchronous preemption loses no XMM state.

### Registry writer cancellation

A process-registry writer that was stopped while waiting could leave its writer-pending mark set when it gave up. Later readers then waited for a writer that no longer existed.

The cancelled writer now clears that mark, and validation stuck-lock reports include task, native-call and held-lock context.

### Panic reporting

The goroutine runtime's panic output no longer decodes the startup object or allocates while reporting an allocator failure. It reads the already-mapped startup handle table and writes stderr through a no-allocation native path.

### Safe-save ownership

Concurrent safe-save users now reserve request-owned temporary names so one transaction cannot consume or clean up another transaction's staging file.

## 9. Deterministic context-save validation

The GC validation suite now has an instruction-hold fixture, `goprobe swaphold`.

Validation kernels expose four validation-only operations, 72 through 75, which use x86 debug-register execution breakpoints and controlled single-step to stop one native thread at instruction boundaries of the goroutine context-save paths. Production kernels answer `Unsupported`.

The probe forces a completed collection at every reachable boundary of:

- `goos_g_swap`: 15 of 15 instruction boundaries, in both switch directions;
- `goos_preempt_entry`: 47 of 47 reachable boundaries; the final failure `UD2` is intentionally unreachable.

The TCG SMP=4 runs and joint eight-vCPU KVM runs completed collections at every counted stop with no lost list. Temporary stack-plan mutations made the fixture fail, demonstrating that the test is sensitive to missing stack roots rather than merely exercising the path.

## 10. Isolated register-root validation

`goprobe regroots` verifies roots that exist in one saved register and nowhere else visible to the test.

It covers:

- XMM0 through XMM15;
- RAX, RBX, RCX, RDX, RSI, RDI, RBP and R8 through R15;
- a native thread;
- a running goroutine;
- a switched-out goroutine whose saved frame is on its G stack;
- negative controls that hold the address in no tested register and must reclaim it.

Fifteen consecutive SMP=4 TCG runs passed all 31 register cases with `lost=0` and all controls reclaimed. Two clean joint KVM runs on eight vCPUs also passed both `swaphold` and `regroots`.

Mutation runs that zeroed snapshot XMM or general-purpose words lost exactly the thread/running-G roots expected from those words; switched-out Gs survived because their registers were already saved on the goroutine stack.

Ordinary userspace function calls are not an additional GC register-root class: caller-saved GPRs and XMM registers are not promised live across the call ABI. The asynchronous preemption/native-entry path has its own explicit save contract and is covered by the instruction-hold validation.

## 11. Validation status

The integrated concurrency work passed:

- ten consecutive joint KVM runs on eight vCPUs after the preemption vector-state fix;
- 20 of 20 TCG `test-goroutine-panic` boots;
- 20 of 20 TCG `gcstress 8` runs;
- the native thread, thread-GC and thread-allocator gates;
- the goroutine runtime, GC and scheduler-aware I/O gates;
- VFS concurrent-read/recovery acceptance;
- the serial VFS boot gate, which reported 471 checks;
- a complete `test-all` on `main` at `39c7036`, including both the production goroutine VFS and the serial VFS fallback;
- later targeted TCG and KVM instruction-boundary/register-root gates through the current context-save coverage branch.

## 12. Known limits

This release does not make every native image a goroutine image. The ordinary native target remains valid and uses native threads explicitly when needed.

The collector is conservative. Pointer-looking words can keep unreachable memory alive; this is expected retention, not memory corruption.

The validation suite exercises goroutine creation and completion under concurrent collection but does not force a collection at every publication or scheduler-bookkeeping instruction. The instruction-hold fixture controls one held thread at a time; it does not construct a single rendezvous with several Ms captured at independently selected switch phases. Once a stop-the-world rendezvous is accepted, the other native threads are already held, so this is a deterministic evidence limit rather than concurrent switching during sweep.

Linux terminal/job-control support remains future work. The release also does not add IPv6, Linux socket syscalls or dynamic ELF linking.
