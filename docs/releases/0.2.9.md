# GoOS 0.2.9

GoOS 0.2.9 is the Linux-interactivity, IPv4-socket, scalability, and build-workflow release.

Starting from the validated 0.2.8 native-concurrency baseline, this release makes the reclaiming allocator scale better across native threads, adds interactive Linux terminals and job control, removes the main VFS directory-listing bottlenecks, adds a capability-confined native SFTP service, brings IPv4 TCP and UDP to the Linux compatibility layer, moves the hottest network paths onto shared-memory rings, raises and classifies several production capacity limits, makes persistent logging production-sized, and turns the build into an incremental, project-local and concurrency-safe workflow.

It also strengthens the stack checker after real crypto code exposed an indexed-SP analysis bug, adds interprocess locking around generated TinyGo compatibility roots, and loads each Linux static PIE at a random base.

## 1. Native allocator and GC scalability

The reclaiming userspace allocator introduced before 0.2.8 now scales its cache and collection policy with the native threads that are actually allocating.

A thread may keep several slabs per size class instead of one. The cache aims for roughly 16 free slots per class and is bounded at four slabs per class, at most 28 pages or 112 KiB per live thread. Eight allocating threads can therefore hold at most 896 KiB in thread-owned slabs.

Collections now have explicit reasons — automatic, explicit, idle and pressure — and the reason determines what is retained:

- an automatic collection may keep slabs owned by threads that allocated since the previous collection;
- explicit, idle and pressure collections take thread slabs back;
- an idle collection runs only when every thread is known to be waiting;
- a collection abandoned before sweep does not advance the GC epoch or clear the allocation marks that determine the next goal.

The automatic collection floor scales with the number of allocating threads instead of keeping the 0.2.8 one-megabyte floor for the whole process. The floor is also capped by one sixteenth of the process page quota, so a large process reaches at most a 4 MiB floor. Large live heaps still use the ordinary approximately-two-times-live goal.

Remote frees are folded while the other threads are held, cached slabs can survive automatic collection without corrupting their mark state, and free pages are discarded while the rendezvous still excludes the other threads. A thread that exits gives its owned slabs back before its slot can be reused.

The KVM allocator workload used for ADR 0205, with 200000 allocations per thread, measured against the 0.2.8 baseline:

| Threads | 0.2.8 | 0.2.9 design | Change | Collections |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 35.2 ms | 35.3 ms | +0.3% | 49 -> 49 |
| 2 | 120.8 ms | 71.4 ms | -41% | 98 -> 49 |
| 4 | 210.3 ms | 121.6 ms | -42% | 196 -> 50 |
| 8 | 875.5 ms | 429.3 ms | -51% | 390 -> 98 |

At eight threads, heap-lock waits fell from 32397 to 17394 and refills from 74.1 to 31.6 per thousand allocations. The validation build kept the longest ordinary pause below one millisecond; the deliberately large-object eight-thread workload reached 1.9 ms.

The trade-off is explicit: a multithreaded process may retain more cheap allocator state between active collections than 0.2.8 did. Idle collection returns that state; the measured eight-thread idle workload stabilized at 147 to 153 pages instead of 102 to 106 in 0.2.8.

## 2. Interactive Linux terminals and job control

Static Linux programs can now run interactively on a GoOS terminal instead of seeing every descriptor as a pipe or file.

GoOS does not add `/dev/pts` or allocate Linux PTY pairs. The native terminal remains the byte transport, while the Linux personality owns the terminal semantics. A foreground Linux job launched alone by the native shell receives a `linux-tty` startup role; the kernel installs descriptors 0, 1 and 2 as one terminal description and tracks its controlling session, foreground process group, termios state, input queue and geometry.

The Linux compatibility layer now implements the terminal operations needed by the tested applications, including:

- `TCGETS`, `TCSETS`, `TCSETSW` and `TCSETSF`;
- `TIOCGWINSZ`, `TIOCSWINSZ`, `TIOCGPGRP`, `TIOCSPGRP` and `TIOCGSID`;
- `FIONREAD`, `TCFLSH` and `TCSBRK` where supported;
- `/dev/tty`;
- process groups, sessions and foreground-group rules;
- stop/continue job control and `wait4(WUNTRACED)`;
- terminal-generated interrupt, quit and suspend signals;
- canonical editing and the non-canonical mode needed by full-screen programs;
- output post-processing including `ONLCR`;
- `SIGWINCH` when the terminal geometry changes.

The native shell switches its session into a transport mode while a foreground Linux program owns the terminal, forwards raw input including Ctrl-C, and restores normal native line handling when the job exits.

Serial, framebuffer and SSH-backed terminals feed geometry into the Linux terminal record. For a serial terminal that cannot otherwise report its size, the terminal service can query the emulator and propagate changes as `SIGWINCH`. The framebuffer path also gained reverse video, underline and a visible cursor, and the installed `goos` terminfo entry was adjusted for ncurses wrapping behavior.

The repository now has scoped compatibility gates for real static binaries:

- BusyBox 1.38.0 interactive `sh`: line editing, foreground process groups, Ctrl-C, `jobs`, `fg`, background work, pipelines and launching nano;
- GNU nano 9.2 built statically with musl/ncursesw: drawing, editing, `fsync` before a reported save, reopening the file, suspend/resume and resize;
- the same nano workload under KVM/Proxmox.

Pipelines, redirected commands and background jobs do not receive the interactive terminal role, so `isatty` remains false there.

## 3. Directory authority and batched enumeration

Directory listing was both an authority hot path and an IPC hot path after 0.2.8.

The VFS previously re-walked subtree scopes while checking a listing entry. Listing 119 entries from persistent FAT32 took 1.41 s under TCG and repeatedly visited protected paths that were unrelated to the directory being listed.

VFS scopes now remember the node identities established by a bounded scope walk. Membership is decided from the returned entry's own node identity rather than inherited from its parent directory. That distinction matters for cross-linked FAT32 directories: an alias outside a protected subtree cannot make protected children visible merely because the listing started from an unprotected parent. Namespace mutations and backend changes invalidate the remembered scope membership.

After removing the repeated authority walks, enumeration itself was still one client request and one FAT32 exchange per entry. VFS protocol 14 and filesystem protocol 12 therefore add batched directory records:

- a batch is bounded to 4096 bytes;
- each record carries the node identity, type, size, timestamps, attributes, mount ID, name and the cursor after that entry;
- FAT32, VFS and Linux `getdents64` preserve the cursor semantics across partial buffers and retries;
- VFS still authorizes every returned node independently, and a hidden name never reaches client-owned memory;
- the batch travels through shared memory that already exists at each boundary rather than through a new allocation path.

The measured 119-entry workload dropped from about 120 client/VFS and 120 VFS/FAT32 listing exchanges to three of each.

Native commands that emit a burst of lines can now use `utility.GatherLines`. Complete lines are coalesced into bounded stream writes of up to 256 bytes, reducing the wake-per-line effect without allocating. In the measured normal build, `ls /apps > /tmp/latency-out` was about 120 ms after batching, with roughly 98 ms attributed to launching the two processes rather than directory enumeration.

## 4. Native SFTP v3 with VFS confinement

The native SSH service now supports the standard `sftp` subsystem without granting filesystem authority to `remoted-worker`.

Each accepted SFTP session launches a separate fixed `/system/services/sftpd` process. PID 1 grants that process:

- one rooted VFS session;
- bounded stdin/stdout relay streams;
- write-only logging authority.

The SSH worker keeps the transport keys and host-signing endpoint but receives no VFS session. A parser or protocol bug in the SSH worker therefore does not gain file access.

SFTP root confinement is enforced in VFS, not in the SFTP parser. `vfs.Authority` can carry a canonical root, and every path-based operation must stay at or below it. A rooted session cannot move or remove its own root and cannot read the mount table. Existing exact/subtree scopes continue to apply by node identity inside the root.

The settings are:

- `system.remote.sftp-enabled`, disabled by default;
- `system.remote.sftp-root`, default `/home/user` and required to be canonical and strictly below `/home`.

A connection keeps the policy generation and root admitted for that session even if the administrator reloads remote settings later.

`sftpd` implements SFTP version 3 with no extensions. Its principal limits are a 64 KiB packet, 32 KiB of file data per READ or WRITE, and 32 open handles. Wire handles contain a slot generation and a random per-session nonce rather than a native handle value. Sequential transfers use bulk VFS I/O, and READDIR consumes the batched listing path from ADR 0208.

Symlinks are not invented for SFTP: SYMLINK, READLINK and extensions are unsupported. SETSTAT changes size only. SCP and shell emulation were deliberately not added because both would require broader command-launch authority.

Failure handling is tied into remote supervision. Loss of the VFS kills the session SFTP processes and closes their SSH channels through the bounded remote shutdown path; loss of a worker kills its SFTP process and releases its VFS session.

## 5. Linux IPv4 TCP and UDP sockets

The Linux compatibility layer now has real IPv4 sockets.

A Linux socket call is translated in the kernel, but transport policy and protocol state stay outside the kernel:

```text
Linux program
    |
    | Linux socket syscalls
    v
kernel/compat/linux
    |
    | GLNXSOCK3 family session
    v
linuxsockd
    |
    | GTCP 4 / GUDP 3
    v
netd
    |
    v
virtio-net
```

`linuxsockd` is a supervised native service. It holds the Linux-socket control state and the native network sessions needed to implement the family, but no VFS, configuration, device, IRQ, DMA or process-launch authority.

A Linux launch receives one network family session. `fork`, Linux threads and `execve` keep that family; an independent launch receives another. If PID 1 cannot grant the session, the program still runs, but `socket(AF_INET, ...)` returns `ENETDOWN`.

The ABI now covers the tested IPv4 TCP/UDP path, including:

- `socket` for `AF_INET` stream and datagram sockets;
- `bind`, `listen`, `connect`, `accept`/`accept4`;
- `getsockname` and `getpeername`;
- `shutdown`;
- `sendto`, `sendmsg`, `recvfrom` and `recvmsg` within the documented vector/control limits;
- blocking and nonblocking connect/accept/read/write behavior;
- `SO_ERROR` and the implemented socket options;
- `FIONREAD`, `FIONBIO` and `SIOCATMARK` on sockets;
- `poll`/`ppoll` readiness and the new `select`/`pselect6` path;
- `eventfd`/`eventfd2`;
- `rt_sigpending`;
- `SIGPIPE`/`MSG_NOSIGNAL` behavior;
- socket inheritance across the supported Linux process model.

Binding a nonzero port below 1024 is refused with `EACCES` because Linux applications run without `CAP_NET_BIND_SERVICE`.

The resolver service now also serves a local DNS endpoint on `127.0.0.1:53`, with TCP fallback when a DNS response is truncated. The boot archive exposes a read-only `/etc` so libc programs can consume the generated resolver configuration. This is what lets the tested BusyBox `wget` and curl workloads resolve names through ordinary libc APIs.

The QEMU Linux-network gate covers 80 checks, including the reference socket behaviors, DNS, TCP and UDP, descriptor inheritance, BusyBox `nc`/`wget`/`httpd`, curl HTTP, and fault/restart paths for the network driver, `netd` and `linuxsockd`.

IPv6, `AF_UNIX`, raw/packet sockets, netlink, `epoll` and ancillary-data support are still outside this release.

## 6. Shared-memory network data planes and targeted wakes

The first Linux socket implementation was functionally correct but crossed too many service/channel boundaries per small operation and moved stream data in small request/reply chunks. 0.2.9 iterated the data plane rather than hiding that cost behind larger timeout values.

### Linux family rings

GLNXSOCK3 keeps the control plane on its channel but moves Linux payload through a shared family pool. Linux writes copy into 16 KiB TX slots and return once the slots are committed to a ring. `linuxsockd` reads ahead into RX slots and the kernel copies directly from those slots into the Linux process. Slot generations and explicit ownership detect stale or duplicate hand-offs.

Socket wakeups are now targeted to waits whose readiness can actually have changed instead of waking every waiter in the family. Linux socket calls also avoid the global stream and shared-memory locks on their ordinary paths. Measured family-lock contention fell from about 4.2 contended acquisitions per TCP request/reply round to 0.07.

### GTCP 4

The native TCP data plane gains GTCP 4. TX, RX, completion, release and readiness state live in shared-memory rings with one writer per control page. The channel carries lifecycle/control operations and doorbells only.

A producer rings the consumer only after the consumer has armed itself for sleep. While both sides remain active, stream data costs no channel message. An in-process 8 MiB comparison recorded 24 channel messages per 64 KiB for GTCP 3 and none for GTCP 4.

`linuxsockd` uses GTCP 4 through its ring link. Ordinary native sessions that need the older per-read features can remain on the older protocol versions.

### GUDP 3

GUDP 3 applies the same ring/doorbell ownership model to datagrams. Its TX and RX pools each contain 16 four-kilobyte slots plus the control page. `linuxsockd` uses GUDP 3; ordinary commands and the resolver can continue to use GUDP 2.

The in-process GUDP 3 test moved 400 datagrams with no channel request on the data path.

### TCP internals

The TCP stack was also reworked so capacity is paid by live connections rather than by a large static table:

- the endpoint registry grows to the highest live slot, up to 4096;
- receive and transmit streams are rings and grow on demand;
- connection, bind, listener, owner and accept-queue lookups are indexed;
- timers live in heaps rather than requiring full-table scans;
- out-of-order data is represented by bounded spans over the receive ring;
- TCP window scaling is negotiated;
- TIME_WAIT four-tuples normally move into separate tombstones instead of occupying the owner's live endpoint quota.

An idle network service therefore no longer reserves buffers for every theoretical TCP connection. ADR 0213 records the stack's static size falling from about 4.9 MiB to 0.55 MiB, with the remainder dominated by UDP receive buffers.

### Measured KVM result

The final HZ=250 KVM measurements recorded after the targeted wakes, GUDP 3 and the narrower lock set were:

| Measurement | Target | Linux path | Native path |
| --- | ---: | ---: | ---: |
| TCP stream, 32 MiB | 258 MiB/s | 298 MiB/s | 497 MiB/s, GTCP 4 |
| TCP one-byte request/reply | 178 us | 232 us | 15 us, GTCP 4 |
| TCP connect/accept/close | 245 us | 301 us | 56 us, GTCP 4 |
| UDP 64-byte request/reply | 144 us | 223 us | 18 us, GUDP 3 |
| write to `poll` waiter return | 248 us | 177 us | — |

Stream throughput and poll wake latency meet the targets; the small TCP round trip, lifecycle and UDP latency do not. The remaining gap is dominated by crossings through `linuxsockd` and `netd` rather than the old family-lock contention. The release records that limit instead of treating benchmark targets as correctness gates.

The default build timer rate is now 250 Hz. Diagnostic builds also gained per-task kernel-call counts/timing and additional network-loop counters used to separate scheduler, locking and service-processing costs.

The native runtime's amd64 memory primitives also gained word/string-instruction implementations for `memmove`, `memcpy` and `memset`.

## 7. Capacity, descriptors, processes and resource policy

Several capacities that had been acceptable as development bounds became too small once interactive Linux programs and sockets exercised them together.

### Linux descriptors

A Linux descriptor table now keeps 64 entries inline and grows in page-backed chunks up to a hard ceiling of 4096 descriptors per process. The default soft `RLIMIT_NOFILE` is 1024. Growth is charged to the owning process and reports Linux-compatible `EMFILE`/`ENOMEM`/`ENFILE` outcomes at the relevant layer.

`select` and `poll` scan large tables in bounded windows instead of allocating a stack-sized array for the process limit.

### Tasks, processes and threads

The scheduler now has 256 task slots represented by four-word task sets instead of one 64-bit mask.

The process table also grows to 256 slots. Linux programs may consume 224 of those slots, with 32 reserved for native system operation, and one Linux family remains bounded to 64 processes. Large Linux process state moved out of static per-slot arrays into lazily allocated pages, so raising the slot count did not simply multiply kernel BSS.

The native thread slot ceiling is 64. Launch profiles now allow:

- 64 tasks in a large process;
- 16 in a normal process;
- one in a tiny process.

Each task after the first is charged for its kernel stack and guard pages.

### Classified resource bounds

ADR 0215 introduces a release rule for capacity constants. Every release-visible bound is classified as protocol, hardware, policy, profile or artifact and records its default, maximum, owner, memory cost, exhaustion behavior and status visibility.

`docs/architecture/resource-policy.md` is the inventory. `tools/resourcepolicy` scans non-test kernel and userspace Go files for package-level `Max*` bounds and makes the unit gate fail when a code bound is missing from the inventory or a documented bound no longer exists.

The document also defines a 1 GiB production reference profile. Current rows include the 256 task/process slots, a 64-thread large process, the 1024/4096 Linux descriptor limits, TCP endpoint and memory policy, listen backlog, logging capacity and other system-wide limits. Numbers that exist only because of the current implementation are recorded as artifacts rather than silently treated as design limits.

## 8. Production-sized logging

The kernel log ring grows to 2048 records. At 208 bytes per entry it costs 416 KiB of kernel BSS, but avoids losing ordinary boot/service records under the larger 0.2.9 workload.

`logd` no longer polls the log by time alone. It waits on a cursor-aware log event, drains the ring in batches, and uses a five-second maintenance wake only for configuration refresh, retry and status work.

Persistent records carry the kernel sequence number so the service can detect gaps, repair a partial final line after a failed write, and resume within the same boot without duplicating already-persisted records.

Persistent history is now four 16 MiB segments by default:

- `system.log`;
- `system.log.1`;
- `system.log.2`;
- `system.log.3`.

The segment size and count are configurable within documented bounds, giving 64 MiB of default retained history. `logd` reports persistence, loss, failure, rotation and repair counters; diagnostic output also exposes kernel ring use and overwrite counts.

## 9. Incremental builds and installed-disk updates

The ordinary development build is now dependency-driven rather than requiring a full rebuild for every change.

Public targets include `kernel`, `userspace`, `initramfs`, `iso`, `recovery-iso`, `system-tree`, `system-image`, `disk` and `disk-update`. `make iso` follows the dependency graph and rebuilds stale components only; component targets remain available when only one artifact is wanted.

Build variants are kept separate, so changing HZ, optimization, diagnostics or validation state cannot silently reuse an artifact from another configuration.

The installed-system tree is reconstructed from current inputs rather than copied over an old tree. A command image left behind in the build directory after its source disappears is therefore not installed merely because the stale file still exists.

`make disk-update` updates an existing installed FAT32 disk from the current system tree while preserving `/home` and `/state`. A disk records the build configuration associated with its last update; a mismatched or previously unassociated disk is refused unless the maintainer explicitly asks to associate it.

The update is intentionally not a transactional filesystem replacement. The VM must be stopped first, the operation is not crash-atomic, and files removed from the current system tree are not deleted from an existing disk. `disk-overwrite` remains the clean-replacement path.

`make test-incremental` validates rebuild isolation and is part of `test-all` and `release-check`.

## 10. Project-local TinyGo cache and reusable compatibility roots

TinyGo's synthetic GOROOT cache no longer grows the user's global `~/Library/Caches/tinygo` merely because GoOS builds temporary compatibility roots at different absolute paths.

Every project TinyGo invocation now goes through `tools/tinygo.sh`. On macOS it supplies a project-local HOME for TinyGo while preserving the real Go module/cache configuration and optional netrc credentials; on other supported Unix hosts it uses the project cache location through XDG. Cache namespaces separate the generated runtime variants.

The generated roots are stable build artifacts:

- `build/toolchains/goroutines`;
- `build/toolchains/crypto`;
- `build/toolchains/tls`;
- `build/toolchains/ssh`.

Their stamps include the relevant source inputs and toolchain identity. Rebuilding one root invalidates only the corresponding synthetic-GOROOT entries. Ordinary builds reuse the root and compiler cache; `make clean` removes the project-local cache and roots.

This bounds the accidental proliferation of `goroot-*` directories caused by random compatibility-root paths. It does not impose a hard byte quota or LRU policy on the normal compiler cache.

## 11. Stack reach, red-zone validation and crypto probes

The stricter userspace stack checker exposed an error in its own handling of indexed SP-relative operands.

`go tool objdump` prints negative 32-bit displacements such as `-140` as `0xffffff74(SP)`. Once the checker decoded that form, it initially rejected `crypto/internal/fips140/sha256.block` in the SHA-256 and ECDSA probes because it treated the displacement without the loop index.

The final checker separates two properties:

- frame/SP depth, which must never be able to skip the 64 KiB userspace guard;
- the 128-byte area below the current SP that goroutine preemption relies on.

It now computes each function's stack reach from SP movement, call return slots and every known SP-relative access. For indexed addressing below the red-zone boundary it accepts the access only when it can prove the relevant loop-counter range. The proof is derived from the machine instruction bytes using the same `golang.org/x/arch/x86/x86asm` revision vendored by Go 1.25.5's objdump, rather than trusting a possibly misleading textual mnemonic.

For `sha256.block` the frame is 232 bytes and the effective reach is 352 bytes. Its indexed loads reach only SP-76 and SP-80; the deeper reach comes from a separate direct access 120 bytes below the current SP.

An access below SP-128 is accepted only in a scheduler-none leaf function without an ordinary call. A preemptible image retains the strict red-zone rule. Unknown run-time changes to SP remain a build failure, and the exact runtime stack-switch/preemption exceptions remain pinned instruction sequences.

`make test-crypto-frames` builds the actual SHA-256 and ECDSA probe ELFs and runs the checker; it is part of `test-all` and `release-check`.

The guest crypto probe run with `CRYPTO_COMPAT=1` passes SHA-256, ECDSA and the other maintained primitive/X.509 probes. The stock TinyGo TLS availability probe still fails for the already documented reason: TinyGo's package is a device-offload shim and is not the native software TLS client used by GoOS.

## 12. Interprocess locking for generated toolchain roots

The incremental build and stable compatibility roots made a second build-system race visible: GNU make orders prerequisites inside one make process, but two independent `make` processes can share one `BUILD_DIR`.

`tools/rootlock` now protects all four generated roots — goroutines, crypto, TLS and SSH — with advisory read/write locks.

Readers hold a shared lock for the complete TinyGo or host-test invocation that consumes a root. Writers hold an exclusive lock while they remove stale stages, generate a replacement, invalidate the matching synthetic-GOROOT cache and publish the new tree.

Publication is atomic on the supported hosts: Linux uses `renameat2(RENAME_EXCHANGE)` and macOS uses `renamex_np(RENAME_SWAP)`. A reader therefore sees the old complete root or the new complete root, never a half-generated tree.

`make clean` takes the four root locks in a fixed order, renames the build tree aside and removes it only after current root users have left. Lock acquisition revalidates the lock-file inode, so a waiter cannot wake on a file that `clean` removed and accidentally create an independent lock generation.

`make test-build-concurrency` exercises genuinely separate OS processes: competing root writers, readers beside forced rebuilds, killed writers, two build directories and `clean` racing an active reader. The lock is deliberately scoped to generated toolchain roots; two independent processes writing the same final ELF are still outside this guarantee.

## 13. Bounded static PIE load randomization

A Linux static PIE (`ET_DYN` without `PT_INTERP`) no longer loads at the fixed `0x40000000` of ADR 0149. Each PID 1 launch and each successful `execve` picks a base from the window `[0x40000000, 0x80000000)` (ADR 0219). The base is a multiple of the image's largest alignment, and the image plus its 64 MiB brk reserve fits inside the window, so the brk contract is unchanged. `fork` and new threads keep the parent's base. `ET_EXEC` images still load at their linked addresses.

The kernel parses the image once at the window start to learn its span and alignment, `linuxelf.PlacePIE` lists the legal bases as an arithmetic sequence, one 64-bit draw from the ADR 0185 generator picks a slot through a 64x64->128 multiply, and the image is parsed again at the chosen base so every hostile-ELF check sees the final addresses. There is no retry loop. The generator seeds from timing jitter, so this works on CPUs without RDRAND. If the generator refuses output, the launch fails; there is no fallback to a fixed base.

A small page-aligned image gets about 2^17.9 possible bases (245,759 for an 8 KiB image). A 64 MiB image whose largest alignment is 2 MiB gets 449. No auxv entry exposes the base; programs derive it from `AT_PHDR`. `goos_diag` builds log `linux pie base=<hex> span=<hex> slots=<hex>` per placement. The build stays free of randomness, so `make test-reproducible` is unaffected.

Stacks, anonymous mappings, shared memory, native images and the kernel image keep their fixed layout.

The new fixture `userspace/linux/pie-probe` is a musl static PIE with its own self-relocating start code. `make test-linux-aslr` boots the default `qemu64` CPU without RDRAND, launches it 32 times, and checks the window, the alignment, at least two distinct bases, a fork child at its parent's base, an exec chain with more than one base, brk, `AT_RANDOM` and `getrandom`. It needs no external binaries and joins `test-all` and `release-check`.

## 14. Other hardening and developer changes

Several smaller changes support the larger features above:

- the terminal relay now drains up to the full 8176-byte output-stream capacity before acting on a request that can print a prompt, so output written before that request cannot be split by a prompt redraw;

- the kernel no longer relies on one fixed firmware load address when locating its own image;
- `WaitAny` can wait for room in a peer channel queue, which is required when `linuxsockd` is backpressured;
- TCP FIN/window-update, delayed ACK, TIME_WAIT and session-teardown paths received regression fixes found by the new ring and KVM tests;
- the network service reports endpoint, memory-budget, lookup and session-use statistics used by the resource-policy and performance gates;
- the shell's `log` command can read the full retained kernel ring in batches;
- failure diagnostics were hardened so a fatal utility diagnostic can still be emitted when ordinary stdout refuses gathered output;
- the README now includes contributor attribution, while architecture, testing, Linux ABI, networking, security, VFS and remote-access documentation were updated alongside the new ADRs.

## 16. Known limits

Linux compatibility remains for static x86_64 ELF programs. Dynamic linking and `PT_INTERP` are not implemented.

Load randomization covers only the base of a Linux static PIE. Stacks, anonymous mappings, `ET_EXEC` images, native images and the kernel keep fixed addresses.

The Linux terminal is an interactive foreground-job integration over the native terminal, not a general Linux PTY subsystem. `/dev/pts`, PTY pairs, `TIOCSCTTY`/`TIOCNOTTY`, output flow control, VTIME semantics and several less-used terminal ioctls remain absent.

Linux networking is IPv4 only. IPv6, `AF_UNIX`, raw/packet sockets, netlink, `epoll` and general ancillary data are not implemented. The final KVM Linux socket stream and poll measurements meet their targets, while small TCP round trips, connection lifecycle and UDP request/reply remain above the aspirational latency targets because the Linux path still crosses `linuxsockd` and `netd`.

SFTP is disabled by default, serves one request at a time per session and intentionally implements only the documented SFTP v3 subset. It does not add symlinks, SCP or arbitrary remote command authority.

The allocator remains a conservative stop-the-world collector. Multithreaded pacing reduces collection frequency but does not make collection concurrent or incremental.

`make disk-update` preserves user/state data but is not crash-atomic and does not remove stale files already present on an installed disk.

The project-local TinyGo cache has no byte-size cap; `make clean` is the retention boundary. Toolchain-root locking protects generated roots and their consumers, not two independent builds writing the same final output file.

The stack checker proves the stack-management properties it owns. For an indexed SP-relative operand whose base displacement is still inside the red zone, ordinary compiler index correctness remains the compiler/program contract rather than a second full x86 data-flow proof.
