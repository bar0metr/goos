# GoOS 0.1.2

This release prepares the storage path for Linux compatibility. Programs run
from the persistent volume, file data between the VFS and the FAT32 service
moves through shared memory instead of messages, and every system service in
the storage stack restarts on failure without taking its clients down with it.

## What changed

### Programs run from the filesystem (ADR 0097)

A command word with a slash is a program path: `/home/demo/args`, or `./args`
relative to the working directory. Under `/system` PID 1 looks in the system
image as before. Anywhere else it reads the file through the VFS into an
executable object, kernel memory that no process maps and that seals itself
when its last byte is written, and names the sealed object in the launch
request. The kernel validates the bytes as a native image exactly as it does
the image's, and still resolves no path.

Only PID 1 can create an executable object: its loader capability is not
transferable. A program read from the filesystem receives its standard streams
and no other grant, whatever its name. A file that is not a regular file, or
whose size changes while it is read, is refused; so is a path in `/system`
outside `/system/bin`, which holds services rather than commands.

### File cache between the VFS and FAT32 (ADR 0098)

File data between the VFS and the FAT32 service no longer moves inside
messages, 224 bytes at a time. The two share a 128 KiB file cache: the VFS asks
the service to fill a 4 KiB slot with a page of a file and serves later reads
of that page itself, without asking again. Writes go through the cache to the
service before they return, as they did, so an error is still reported by the
write that caused it.

### Services restart without taking their clients down (ADR 0099, 0100, 0101)

In 0.1.1 the VFS and the block service did not restart, and the configuration
and log services were registered to restart but could not: their first launch
consumed the sessions they needed. A fatal error in the VFS, the block service,
the driver or the FAT32 service spun instead of exiting, so no supervisor could
replace it and every client waited out its deadlines.

Now every system service exits when it cannot go on and is restarted, and PID 1
renews what the new instance needs. Clients are not restarted with it: the
shell, the configuration service and the log service are handed new sessions
over channels they already hold with PID 1, so the shell keeps its jobs and
working directory. When the VFS restarts the FAT32 service restarts behind it;
when the block service restarts the driver and the FAT32 service do. A service
started again in the same boot sees `RESTART=1` in its environment, and the log
service uses it to resume after the last record in its file rather than write
the kernel ring out again. Each restart took 15 to 20 ms under QEMU TCG.

### Fixes

- Open files in the VFS belonged to no one: any session could use a handle
  another had opened, one session could fill the whole table of 64, and the
  files a crashed process left open stayed open. Each file now belongs to the
  session that opened it, a session holds at most 16, and they close when the
  session goes.
- `cp` stopped after a few hundred bytes of a larger file, exhausting its
  memory, and left the target truncated. `ls` and `stat` did the same on a
  large directory or tree. All three now reuse their memory for each exchange.

## Compatibility

The native environment of 0.1.1 is preserved; volumes written by 0.1.1 mount
unchanged. Wire formats that changed, all internal to the system image:

| Interface | Version | Change |
| --- | --- | --- |
| native calls | — | `ExecutableCreate` (37) and `ExecutableWrite` (38) added |
| exec protocol (shell to PID 1) | 10 | a stage may name any canonical absolute path |
| filesystem-service protocol `GFSPRT01` | 2 | messages name file-cache slots and carry no data |
| VFS control protocol | 5 | session notice added |
| configuration control protocol | 2 | session notice added |

PID 1 holds two more initial handles: the loader capability (`0x100000017`)
and the file cache (`0x100000018`). The lifecycle launch request is unchanged.
The native ABI is still not declared stable.

## Performance

Measured under QEMU TCG at 100 Hz against 0.1.1 on the same host, both disk
images on one host volume (medians):

- A 16 KiB read of a file on the volume: 54.2 ms before, 9.4 ms now, as long
  as a read of the memory-resident system image.
- `bench read` of a small persistent file: 574 µs before, 488 µs now.
- Command launches, IPC ping-pong, stream throughput and persistent writes:
  unchanged within noise. The timer configuration is unchanged.
- A 22 KiB program starts from `/home` in about 113 ms, against 14 ms from
  `/system/bin`: PID 1 reads the file from the VFS 224 bytes per exchange.

## Known limitations

Everything listed for 0.1.1 still holds, except that programs are no longer
limited to the system image, file data between the VFS and FAT32 no longer
moves through messages, and the VFS restarts. In addition:

- A program on the persistent volume is at most 64 KiB, the FAT32 service's
  file limit; one in `/tmp` at most 4 KiB, RAMFS's. The kernel accepts up to
  1 MiB.
- A program is read from its file on every launch, one IPC exchange per 224
  bytes, and PID 1 answers nothing else while it reads.
- A file rewritten at the same size while it is being read can launch as a
  mixture of both versions. It is validated either way and runs with its
  standard streams only.
- File data between a program and the VFS still moves 224 bytes per exchange;
  the file cache ends at the VFS.
- A VFS restart empties `/tmp`, which lives in the VFS, and closes the files
  open at the time; commands running then fail their next filesystem request.
  A write in flight when the VFS, the FAT32 service or the block service dies
  fails and may be partly applied.
- A setting changed and not yet written when the configuration service dies is
  lost.
