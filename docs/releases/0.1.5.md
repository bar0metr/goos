# GoOS 0.1.5

GoOS 0.1.5 adds an interactive graphical text console for the UEFI/QEMU boot
path. It preserves the existing userspace TTY, capability model, serial
diagnostics, process isolation, and native application ABI.

## Graphical console

The UEFI loader discovers Graphics Output Protocol before
`ExitBootServices`, validates firmware-provided geometry and pixel metadata,
and selects a usable 32-bit linear mode in a deterministic preference order.
The preferred mode is 1280x800, with bounded fallbacks through 1280x720,
1024x768, 800x600, the current usable mode, and another usable mode.

The kernel preserves the framebuffer across page-table replacement and maps
only its visible stride range at a dedicated kernel virtual address. The
mapping is supervisor-only, writable, NX, and uncached. Process page-table
roots do not inherit it, and framebuffer device memory is excluded from PMM
allocation.

The framebuffer package provides clipped pixel, rectangle, clear, glyph, and
scroll operations. The terminal renderer handles incremental UTF-8, malformed
input replacement, wrapping, scrolling, carriage return, newline, backspace,
tab, and the bounded cursor and erase sequences used by the userspace TTY.
Console output is written to COM1 first and mirrored to the framebuffer when
graphics is available.

## Font and terminal geometry

The console embeds the Spleen 12x24 bitmap font. Its selected subset covers
printable ASCII, Russian Cyrillic including `Ё` and `ё`, and a visible
replacement glyph. Spleen remains under its upstream BSD 2-Clause license;
copyright and complete license terms are recorded in
[`docs/third-party-font.md`](../third-party-font.md).

The capability-checked `ConsoleInfo` operation exposes only terminal columns,
rows, and availability flags. The userspace TTY uses the active geometry to
erase and restore every framebuffer row occupied by wrapped edited input. A
serial-only boot retains the 80x25 fallback.

## Interactive keyboard

QEMU graphical input uses the emulated i8042 PS/2 controller. Initialization
is bounded, scanning uses scan-code set 1 translation, and steady-state input
is interrupt-driven through IRQ1. The decoder supports the US alphabet,
digits, punctuation, both Shift keys, Caps Lock, Enter, Backspace, Tab,
Ctrl-C, Ctrl-D, Ctrl-L, Ctrl-U, and arrow-key CSI sequences.

PS/2 and COM1 publish into one bounded logical console input queue. The
userspace TTY remains the sole owner of line editing, sessions, foreground
process selection, prompts, and Ctrl-C policy. Shells and ordinary commands do
not receive I/O-port, IRQ, or framebuffer authority.

## QEMU graphical mode

`make run-gui` opens QEMU's graphical display while leaving COM1 attached to
the host terminal. `make run` remains headless for automation and recovery.
The graphical display backend is configurable through `QEMU_DISPLAY`.

`make test-console-gui` remains headless. It captures a QEMU monitor
screendump and verifies exact validation-only checkerboard pixels without OCR.
It then injects editing keys and a shell command through QEMU's PS/2 path;
serial output proves that input traversed IRQ1, the decoder, console queue,
TTY, and shell.

## Validation

Host tests cover GOP metadata and mode selection, framebuffer bounds and guard
words, glyph coverage, UTF-8 and terminal parser state, scrolling, wrapped
cursor movement, scan-code translation, modifier state, malformed keyboard
streams, and mapping permissions. Validation boot additionally proves the
framebuffer mapping survives CR3 replacement but is absent from process roots.

The release gate includes reproducible clean builds, lint, documentation,
unit, integration, security, FAT32 and partition coverage, storage stress,
the serial boot suite, graphical pixel and keyboard validation, and the QEMU
stress matrix.

## Remaining limitations

- The graphical interface is a text console, not a GUI.
- GOP mode selection occurs only during boot; runtime mode changes are absent.
- Rendering is CPU-driven and supports only validated linear 32-bit GOP modes.
- Virtio-GPU, USB keyboards, mice, multiple virtual consoles, and PTYs are not
  implemented.
- The keyboard layout is fixed to US, and graphical input is QEMU-focused PS/2.
- Font coverage is intentionally incomplete; unsupported Unicode uses the
  replacement glyph.
- COM1 remains the primary debug and recovery console.
- Real-hardware graphics requires compatible UEFI GOP. Broad real-hardware
  keyboard compatibility is not claimed.
