# GoOS 0.1.0

The first release. It covers the feature set of specification §56 and its §57
demonstration, which the boot test runs on every build.

## What it is

A capability-based operating system for `x86_64`, with the kernel and all
userspace written in Go and built with TinyGo. It boots from a UEFI ISO under
QEMU with OVMF.

- **Kernel:** preemptive round-robin scheduling, processes and tasks, per-process
  address spaces with NX and W^X, and generation-safe handles with
  capabilities and rights. It provides typed, versioned IPC with handle
  transfer, shared-memory objects, reference-counted byte streams, and
  per-process resource quotas.
- **Services:** all run in userspace under a supervisor in PID 1 that restarts
  them: the VFS, a RAMFS root, the read-only `/system` image, the block service
  with a capability-scoped virtio-blk driver, a FAT32 persistent volume for
  `/home` and `/state`, the structured log service, the typed configuration
  service, and the terminal service.
- **Shell:** native, with pipelines, redirection, background jobs, and
  twenty base utilities, each a separate image under `/system/bin`. `reboot` and
  `poweroff` flush storage first.

## Security properties

- No ambient authority. A process reaches only the objects whose capabilities
  it was given; there is no root.
- Memory safety comes from Go. `unsafe` is confined to the architecture,
  memory-management and firmware packages, and each use is justified in place.
- The host and boot tests attack the isolation boundaries: cross-process memory,
  forged and stale handles, malformed IPC, oversized requests, full queues,
  malformed images and volumes, crashing services and drivers, and user and
  kernel stack overflows.
- Every stack has an unmapped guard. The build rejects any stack frame that
  could step over it. A kernel stack overflow is reported with the guard
  address it hit (ADR 0088, ADR 0091).

## Building

```bash
make toolchain-check
make
make run
```

`make test-all` is the full gate. The build is reproducible: two clean builds
are byte-identical (`make test-reproducible`). TinyGo's `-opt=2` is the
default; `make OPT=z` builds the smallest variant (ADR 0090).

## Known limitations

- One CPU, QEMU q35 only. Real hardware is not a target yet.
- Services that start before the terminal, and the kernel's warning echo,
  still write the console directly, so their output can land in a line being
  typed. The terminal's redraw assumes the edited line fits one row (ADR 0089).
- A kernel stack overflow is reported, but the kernel cannot recover from it.
- Linux ELF compatibility has not started. It is the next milestone.

The list above understated what 0.1.0 does not do. Stated explicitly, as
released (the threat model has the detail):

- No Linux ABI compatibility of any kind: no Linux ELF loading, syscall
  translation, or file descriptors.
- No SMP: the kernel runs one CPU inside one exclusion domain.
- No IOMMU: a compromised storage driver's DMA is not confined to its buffers.
- No ASLR: the kernel and user address layouts are fixed, including the image,
  shared-memory, DMA, and system-image windows.
- No verified or Secure Boot chain: the kernel, the boot archive, and the
  images in it are not signed or measured.
- CPU time is accounted per process but never limited.
- PID 1 holds every initial capability and remains a single point of
  authority; compromising it grants what it holds.
- Architectural shortcuts that 0.1.1 removes: the kernel resolved every
  executable path in the boot archive itself; the FAT32 parser ran inside the
  VFS process, which also held the block endpoint; PID 1 printed through
  `DebugWrite`, authorized by comparing address-space roots rather than by a
  capability; and userspace `unsafe` was spread across every service and not
  checked by lint.
